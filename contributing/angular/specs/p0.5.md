# P0.5: test wiring

Playwright has an `angular` project that runs every spec whose fixture exists, the planner knows which changes reach Angular, and a spec on an Angular page fails when Angular reports an error.

## Settled

- **One project for now.** `angular` joins `frameworks` in `tests/playwright.config.ts`. `angular-ssr`, `angular-data` and `angular-sheet` arrive with their fixtures, in 3A.1, 3B.1 and 3B.4.
- **The planner list.** `angular` joins `frameworks` in `scripts/affected-specs.mjs`, so a change under `packages/angular/` reaches Angular alone. `chromiumProjects` returns only the base project for it, until 3D.5 adds the rest.
- **No leak run without a leaks fixture.** The planner now leaves a framework out of the leak run when `fixtures/leaks/<framework>.ts(x)` doesn't exist. Without that, a run of `leaks.spec.ts` on `angular` alone finds no test and fails.
- **Console-error capture.** An automatic fixture in `tests/fixtures.ts`, like `solidDiagnostics`. On a project whose framework starts with `angular`, it records console errors and uncaught errors that match `/^ERROR\b|\bNG0\d+/`, from before the page loads, and fails the spec if any was recorded.
- **Why that pattern.** In `@angular/core` 22.3.0, the default `ErrorHandler` calls `console.error("ERROR", error)`, and `formatRuntimeError` starts every Angular error with `NG0` and its code. A page's other console errors, like a failed image request, stay out, since specs such as Avatar's cause them on purpose.
- **No allowance yet.** Solid's `allowSolidDiagnostic` has no Angular twin. The first spec that needs one adds it.

   The throwaway fixture was plain DOM with a "Before" button, and both it and the spec are deleted. On `angular`, a clean page passed, and so did a console error without Angular's marks. An `ERROR` logged while the page loaded failed the spec, as did one logged later and an uncaught `NG0203`. On `solid`, all five passed, since the capture is off there.

   The planner, with temporary files: an Angular fixture plans `specs/(tabs)\.` with `--project angular` among the others and a leak run without it. A file in `packages/angular/src` plans the whole `angular` project. With a React manifest change beside the fixture, no leak run names `angular`. Every project a plan names is one the config defines.

4. **Spec counts.** When this task was built no Angular fixture existed, so nothing ran on `angular` beyond the throwaway spec. `tabs.spec.ts` on `solid` was unchanged since P0.3: 40 passed.
5. **Known gaps.**
   - **The proof was half met until P0.4.** With no Angular fixture the list held only `web-popups.spec.ts`. Since P0.4 it holds the five Tabs files that open `tabs` as well: 61 tests in 6 files.
   - **The capture first saw Angular in P0.4.** Here it was tested with messages shaped like Angular's, taken from its source. P0.4 repeated the test on a real Angular page, with an error thrown in a listener and a token nobody provides, and both failed the spec.
   - **The whole `react` project** ran after this task for the change to `tests/fixtures.ts`, which every spec imports: 2,908 passed, 106 skipped and 7 failed. Three of the seven passed when run again alone. The other four fail the same way on the untouched tree: two Drawer touch tests and two of Radio's tab stop tests.
6. **Questions.** A base fixture such as `tabs/react.tsx` reaches every framework in the planner: `frameworksOf` compares the file name with its extension, so only `react-*.tsx` helpers map to React. `angular.ts` behaves the same. Is that meant?
